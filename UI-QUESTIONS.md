Design: plan and question cards share `src/components/ui/agent-card.css`: the same raised outer panel, radius, edge and shadow. Fluid owns the question’s internal padding, heading, progress, rows and footer; plan-specific header/icon/action styling stays confined to PlanCard. Question answers sit directly on the outer surface; only the plan preview has a sunken inset. Questions use the actual vendored Fluid Functionalism `AskUserQuestions` component, including its rows, inline multi-line custom answers, free-text input, navigation, keyboard shortcuts, and Fluid buttons. `ElicitationForm` adapts provider schemas and typed responses. The host supplies only the plan-card outer surface; explicit submission allows an option plus a note, while standalone component consumers retain Fluid’s immediate single-choice behavior. The implementation is based on the public rendered references, without copying gated Kobra source.

References: [Fluid question flow](https://www.fluidfunctionalism.com/docs/ask-user-questions), [Kobra question card](https://kobra.systems/components/question-card), [Grok wire types](https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-tools/src/implementations/grok_build/ask_user_question/types.rs).

## Codex Default-mode async question recovery — October 27, 2026

The reported chat contained a real `request_user_input_async` function call and an `{accepted:true}` native result. The installed `codex-acp 2.1.1` emitted only the final prose over ACP. Inspection of the published `2.3.0` adapter found the same omitted native `agentMessage.questions` path. The earlier native question acceptance used Codex Plan mode and did not cover this path.

A version-gated Codex bridge reads accepted question receipts from the exact native thread’s local rollout, verifies its session ID and workspace, and reads a bounded 8 MiB tail. It observes active prompts once per second and also checks completion and reconnection. Receipt content is validated as question data. Failed, malformed, unmatched and previously answered calls do not create forms. A later native user message supersedes prior receipts. The bridge does not change the model catalog or global CLI configuration. It is enabled only for the inspected ACP 2.1.1 and 2.3.0 versions and requires local native session receipts. The tested CLI is 0.164.0.

Questions stay pending after a final message and across history replay. Explicit answers/dismissals are persisted by question ID. Shutdown preserves unanswered async questions for recovery. Replies after completion use the original ACP session; replies during work use the adapter’s advertised `_session/steering` extension. The rare steering/completion race is tracked against real native turn completion. No synthetic native server response is sent to a tool that already returned accepted.

Both authenticated Default-mode tests passed with GPT-6.1 Terra: an answer after turn completion and an answer injected into a running turn. Each confirmed Blue and its distinct note marker. The active case reported `{outcome:"injected"}`. Rust tests cover receipt validation, native identity/workspace checks, incomplete writes, pending lifecycle, single-use answers and stored dismissal IDs. A frontend regression reproduced the completion-clearing bug before the fix and now passes. The full frontend suite passes 440 tests; the Rust suite passes 109 tests plus its compile-fail doctest, with 9 opt-in tests excluded from that default run.

Native packaged-app acceptance: rebuilt and relaunched the signed debug Harbor bundle, then reopened the exact reported chat, “Ask dummy question using tool” (`33ebabff-8fe2-4efe-afd3-e97d73746411`). Without sending another prompt or changing collaboration mode, the previously missing “Dummy question: Which color do you prefer?” card appeared with Blue/Green/Red, custom input and Submit answers. Native accessibility state and the rendered screenshot both confirmed it. The card was left unanswered for the user.

## Number chips and Continue shortcut — October 27, 2026 (Q10)

The previous visual comparison measured the parent button but missed the nested keycap. Before this repair its computed style was 13px SFMono and dim gray, despite the component’s 11px sans-serif/light-text classes: the unlayered global `kbd` reset took precedence over Tailwind utilities. Moved that fallback to the base layer. The keycap now computes to 11px Inter with the same foreground color as the primary button’s label. This lets each Fluid component retain its own keycap styling.

Harbor’s explicit-submit flow now uses the reference’s outlined numeric badges, filled for a selected option, for both radio and checkbox questions. Selection semantics remain unchanged: single-choice stays exclusive, and multi-select supports multiple values. Standalone immediate single-choice consumers retain their original plain-number hints. The adapter labels every primary question action Continue, including the final answer. Existing Skip/Cancel outcomes and option-plus-note transport remain available.

The updated interaction tests failed against the old label before the repair and pass afterward. All 440 frontend tests pass. The three-provider browser check now verifies the actual nested keycap font and contrast, filled and outlined badge states, Continue label, notes, retry and keyboard submission; light/dark, narrow layout and accessibility coverage also pass. Viewed the [final light card](screenshots/questions/fluid-chips-continue-light.png). The signed debug app builds and was restarted; the original chat visibly shows the filled Red badge and a legible Continue shortcut. Its pre-restart Red draft was restored without submitting an answer. Browser task space 168 was finished with no retained tabs.
